# Plan Mode 模板

触发：当前是 Plan / 规划 / 先出方案 / 不要改代码；或任务将改接口契约、Prisma、跨模块、公共 util、已有 endpoint、或合计将触及 ≥3 个业务文件。

豁免（可直接实现，仍遵守 Boundaries）：只改注释/文案、只改一个已确认无外部引用的 private 函数、只改测试断言且不改生产代码。

硬约束：

- 只读。禁止 Write / Edit / 会改仓库或数据库状态的命令。禁止「先改一点再补计划」。
- 计划未获用户明确批准（「按此执行」/ `LGTM` / `build`）前，不得进入实现，也不得先落测试文件。
- 未列出将读取的文件并得到确认前，只打开当前链路相关文件；读 + 改 + 新增测试合计 ≤ 8。
- 先读 `docs/integration.md` 对应节。契约以本仓库实现 + Swagger 为准。
- 不要猜测前端实现。前端只标注应对齐 `docs/integration.md` 哪一节。
- 上一轮批准不自动带到本轮。用户新消息 = 新计划，除非用户写「按上次 plan 执行」。
- 实现必须按已批准 plan 的文件表逐项改；新增文件或偏离 plan 时先停，更新 plan，再等确认。
- Plan 必须自包含，禁止用「如上所述」省略文件表。Plan 只写文件级意图与验收，不贴大段将写入的完整实现代码。

## 不确定就问（禁止擅自定需求）

必须先问、禁止自己选「最佳实现」：

- 需求、验收标准、错误码/状态码、字段含义或默认值不明确
- 兼容策略不明确（兼容旧调用方 vs breaking）
- 是否改 Prisma / 统一响应 / JWT / 已发布契约 / WS 事件不明确
- 测试范围或是否要 e2e 不明确

可以自己定、不必问：

- 符合本仓现有分层、命名、DTO、测试文件摆放的写法
- 局部变量、函数拆分、与现有 spec 同样风格的断言

一次最多 3 个阻塞问题；能并行的合并成 A/B 选项并给推荐。未回答前不得把猜测写进文件表，也不要先写代码。

## TDD（批准之后才执行）

顺序固定，不允许颠倒：

1. 按 plan 先写/改会失败的测试：模块内 `*.spec.ts`。仅当跨模块鉴权/契约变化时加 e2e（`npm run test:e2e`）。不要发明仓里不存在的测试体系。
2. 先跑测试，确认新断言为红（或写明为何无法先红，例如只补已有用例）。
3. 再写实现。
4. 再跑同一批测试，必须变绿。
5. 覆盖率只计本次改动的源码文件（不含 `*.spec.ts`、生成物）。有 coverage 脚本才测；没有则跑相关测试并注明「无法测覆盖率」，禁止口算 90%。
6. 有 coverage 脚本时，改动文件行覆盖率目标 90%。达不到先补测试；仍达不到则列出未覆盖分支和原因，Ask first，不得假装达标。

豁免 TDD 先红：纯文档 / 注释 / Swagger 描述文字；只改类型名且现有测试已覆盖（先跑现有测试即可）。禁止为冲覆盖率测试私有实现细节、Prisma 生成物，或对外部网络做真调用。Plan 第 4 节必须列出将写的测试文件与要锁的行为（成功 / 鉴权失败 / 校验失败 / 旧调用方兼容），并计入 8 文件上限。

每次 Plan 必须按下面模板输出，缺任一块视为未完成。仅当实现路径 ≥2 或存在兼容分叉时强制第 3 节双方案。

### 1. 目标与非目标

- 要做成什么（可验收的一句话）
- 明确不做的事
- 列出假设（可被用户一句否决）

### 2. 现状（必须有文件路径）

- 相关现有行为，引用 `path`
- 已读文件列表（路径 + 为什么读）
- 公共符号的引用搜索结果（util / service 方法 / DTO / 路由）

### 3. 方案对比

每个方案写：改动面、对契约 / DB / 已有调用方 / 前端联调的影响、风险。给出推荐方案 + 理由 + 淘汰理由。默认选向后兼容方案；选 breaking 必须写清理由并放入「待确认」。

### 4. 完整代码修改方案（必须穷尽）

| 文件    | 动作           | 具体改什么                                        | 理由                 | 风险 / 回滚 |
| ------- | -------------- | ------------------------------------------------- | -------------------- | ----------- |
| src/... | 改 / 新增 / 删 | 函数、DTO、路由、字段级说明，禁止只写「调整逻辑」 | 为什么必须动这个文件 | 影响面      |

另外必须写清：

- 不改的文件，以及为什么不改
- 接口契约是否变化；若变，对齐 `docs/integration.md` 哪一节、Swagger 哪条
- 是否需要 migration；若需要，schema 字段级说明
- 调用方影响：本仓引用点（路径 + 符号）；是否被 Swagger / `docs/integration.md` 暴露；其他端是否必须同步；兼容策略（加可选字段 / 新 endpoint / 默认参数 / 弃用期 / breaking）
- 测试计划：改 / 补哪些 `*.spec.ts` 或 e2e、要锁的行为
- 将跑的精确验证命令
- 发布注意：是否双写、是否需要前端同发
- 文件总数是否 ≤ 8；超出则拆任务或先问

### 5. 执行顺序

编号步骤，每步写依赖和完成标准（新测试先红、实现后变绿、Swagger 与一致、旧调用方仍能用）。

### 6. 待确认问题

有歧义先提问。没有问题则写：「无，可批准执行。」

结束语必须是：

> 以上为完整修改方案，等待确认后再改代码。

计划不合格（缺文件表、缺理由、缺测试计划、缺调用方影响、该对比时缺方案对比）：停止，按模板重出，不要改代码。
