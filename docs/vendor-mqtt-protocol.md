# 设备端 MQTT 对接文档

## 1. 连接配置

| 参数 | 说明 |
|------|------|
| Broker | MQTT Broker 地址（由服务端提供） |
| ClientID | 设备唯一标识，建议使用设备Mac地址 |
| Username | 认证用户名（可选） |
| Password | 认证密码（可选） |
| KeepAlive | 30秒 |
| CleanSession | false（持久会话） |
| QoS | 1（至少一次） |

## 2. 接入顺序与主题定义

### 2.1 接入顺序

**MQTT 连接成功后，设备必须先向 `loginMac` 主题上报设备标识，再开始状态上报、心跳和业务指令交互。**

| 步骤 | 设备操作 | 说明 |
|------|----------|------|
| 1 | 建立 MQTT 连接 | 使用第1节的连接参数连接 Broker |
| 2 | 发布设备绑定消息 | 连接成功后的第一条业务上报，主题为 `loginMac`，消息仅包含 `device`，见第3节 |
| 3 | 订阅设备下行主题 | 订阅 `device/down/{mac}`，用于接收服务端业务指令 |
| 4 | 上报设备初始状态 | 向 `device/up/{mac}` 发布 `query` 消息，上报电量、音量和版本 |
| 5 | 进入正常交互 | 每5秒上报 `query` 心跳，并处理服务端下发指令 |

绑定结果的服务端下发参数暂未定义，当前流程未定义等待绑定业务应答的步骤。MQTT 发布确认与服务端完成设备绑定属于不同层面的结果。

### 2.2 主题定义

| 使用顺序 | 方向 | 主题 | 消息用途 | 说明位置 |
|----------|------|------|----------|----------|
| 首先上报 | 设备 → 服务端 | `loginMac` | 上报设备标识，供服务端绑定设备 | 第3节 |
| 后续接收 | 服务端 → 设备 | `device/down/{mac}` | 接收查询、音量设置、重启、升级及恢复出厂设置指令 | 第6节 |
| 后续上报 | 设备 → 服务端 | `device/up/{mac}` | 上报设备状态和心跳 | 第5节、第8节 |

`{mac}` 为设备Mac地址，与绑定消息的 `device` 值保持一致。本文示例统一使用 `AABBCCDDEEFF`。

所有消息均使用 UTF-8 编码的 JSON 字符串。设备绑定消息与后续业务消息的结构分别见第3节和第4节。

---

## 3. 设备绑定上报（连接后首先执行）

设备在 MQTT 连接成功后，首先通过独立主题 `loginMac` 上报设备标识，供服务端绑定设备。初次连接和断线重连成功后均按第2.1节顺序执行。

**发布主题**: `loginMac`

**方向**: 设备 → 服务端

上报 JSON 目前仅包含 `device` 字段。消息结构如下：

```json
{
  "device": "AABBCCDDEEFF"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| device | string | 是 | 设备标识（deviceid），值为设备Mac地址，与设备上下行主题中的 `{mac}` 保持一致 |

**服务端行为**: 接收设备标识，用于绑定设备。

**服务端下发**: 参数暂时预留，下发主题、消息结构和处理规则待后续确定。

---

## 4. 后续业务消息格式

完成设备绑定上报后，设备通过上下行主题进行业务交互。

### 4.1 通用消息结构

以下结构适用于 `device/up/{mac}` 和 `device/down/{mac}`；`loginMac` 的独立消息结构见第3节。

```json
{
  "cmd": "query",
  "flag": "success",
  "data": null
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| cmd | string | 是 | 命令类型，见下方命令列表 |
| flag | string | 是 | 状态标志：`"success"` / `"fail"` |
| data | object/null | 否 | 命令相关数据，无数据时为 `null` |

### 4.2 命令列表

| cmd | 说明 | 方向 | data |
|-----|------|------|------|
| `query` | 电量/音量/版本查询 | 双向 | 见下方 |
| `volume` | 音量设置 | 双向 | 见下方 |
| `restart` | 重启设备 | 服务端→设备 | null |
| `upgrade` | 固件升级 | 双向 | null |
| `recover` | 恢复出厂设置 | 服务端→设备 | null |

## 5. 设备状态上报

### 5.1 电量、音量和版本上报 (query)

设备定时或触发上报电量、音量、固件版本信息。

**发布主题**: `device/up/{mac}`

```json
{
  "cmd": "query",
  "flag": "success",
  "data": {
    "battery": 80,
    "volume": 50,
    "version": "1.2.3",
    "charging": false
  }
}
```

| 字段 | 类型 | 范围 | 说明 |
|------|------|------|------|
| battery | int | 0-100 | 电量百分比 |
| volume | int | 0-100 | 音量百分比 |
| version | string | - | 固件版本号，格式 x.y.z |
| charging | bool | true/false | 是否正在充电。**2026-11-11 约定增补**：机芯厂待实现；未上报时服务端按 `null` 处理，不影响既有链路 |

**服务端行为**: 更新设备电量、音量、版本信息，推送状态到App端，如有新固件则自动下发升级指令。

## 6. 服务端下发指令详解

设备需订阅 `device/down/{mac}` 主题接收以下指令。

### 6.1 查询指令 (query)

服务端请求设备上报电量、音量、版本信息。

```json
{
  "cmd": "query",
  "flag": "success",
  "data": null
}
```

**设备行为**: 收到后应立即上报一条 `query` 消息（见第5.1节）。

---

### 6.2 设置音量 (volume)

```json
{
  "cmd": "volume",
  "flag": "success",
  "data": {
    "volume": 50
  }
}
```

| 字段 | 类型 | 范围 | 说明 |
|------|------|------|------|
| volume | int | 0-100 | 目标音量值 |

**设备行为**: 设置音量到指定值。

---

### 6.3 重启设备 (restart)

```json
{
  "cmd": "restart",
  "flag": "success",
  "data": null
}
```

**设备行为**: 重启设备。

---

### 6.4 固件升级 (upgrade)

```json
{
  "cmd": "upgrade",
  "flag": "success",
  "data": null
}
```

**设备行为**: 触发OTA固件升级流程。

---

### 6.5 恢复出厂设置 (recover)

```json
{
  "cmd": "recover",
  "flag": "success",
  "data": null
}
```

**设备行为**: 恢复出厂设置，清除所有用户数据。

## 7. 完整交互流程示例

### 7.1 连接、绑定与设备上线

以下按设备执行顺序展示；断线重连成功后同样先执行绑定上报。

```text
1. 设备建立 MQTT 连接，连接成功。

2. 设备 → 服务端  topic: loginMac
{
  "device": "AABBCCDDEEFF"
}

3. 设备订阅下行主题：device/down/AABBCCDDEEFF

4. 设备 → 服务端  topic: device/up/AABBCCDDEEFF
{
  "cmd": "query",
  "flag": "success",
  "data": { "battery": 85, "volume": 60, "version": "1.0.0" }
}

5. 服务端 → 设备  topic: device/down/AABBCCDDEEFF  (如有新固件)
{
  "cmd": "upgrade",
  "flag": "success",
  "data": null
}

6. 设备进入正常交互，每5秒通过 device/up/AABBCCDDEEFF 上报 query 心跳。
```

## 8. 心跳保活与在线判定

### 8.1 心跳机制

设备完成连接后的绑定上报后，需**每 5 秒**向服务端上报一条 `query` 消息作为心跳，服务端据此判定设备在线状态。

```json
{
  "cmd": "query",
  "flag": "success",
  "data": {
    "battery": 80,
    "volume": 50,
    "version": "1.2.3"
  }
}
```

### 8.2 在线判定规则

| 条件 | 判定结果 |
|------|---------|
| 服务端在 15 秒内收到设备上报消息 | 设备在线 |
| 服务端超过 15 秒未收到设备上报消息 | 设备离线 |

- 服务端每 5 秒扫描一次在线的 MQTT 设备，检查最后活跃时间
- 超过 15 秒（3倍心跳间隔）未上报的设备将被标记为离线
- 设备重新上报消息后自动恢复为在线

### 8.3 注意事项

- 设备**必须**定时上报 `query` 消息，即使电量/音量/版本未变化
- 建议上报间隔 5 秒，不要超过 10 秒，否则可能被误判为离线
- MQTT Broker 的 KeepAlive 仅保证 TCP 连接存活，服务端在线判定依赖应用层心跳

---

## 9. 注意事项

1. **QoS 级别**: 建议使用 QoS 1，确保消息至少送达一次
2. **Retained 消息**: 不使用 retained 标志，避免设备上线后收到过期指令
3. **心跳保活**: 设备需每 5 秒上报 `query` 消息作为心跳（见第8节）
4. **断线重连**: 建议实现自动重连机制，重连成功后先向 `loginMac` 上报设备标识，再重新订阅 `device/down/{mac}` 并恢复状态上报和心跳，执行顺序见第2.1节
