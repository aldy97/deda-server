# 【后端 Bug 排查】家长报告“昨日分钟”与近 7 日趋势数据不一致

## 一、问题摘要

小程序「更懂TA」页面中，同一设备、同一天的时长数据出现矛盾：

- **昨日家长报告显示：昨日使用 3 分钟。**
- **近 7 日趋势中，10 月 31 日显示：0 分钟。**

两个数据分别来自不同接口。前端没有进行换算或 Mock，因此需要后端核查两个接口的统计口径和数据源。

---

## 二、问题发生情况

### 页面与设备

- 页面：「更懂TA」→「昨日家长报告」
- 设备 ID：`dev-local-001`
- 孩子：乐乐
- 报告日期：`2026-10-31`
- 页面同时显示昨日有 **5 次自由对话互动**，说明该日并非完全没有使用记录。

### 接口一：家长报告

```http
GET /learning-stats/parent-report?deviceId=dev-local-001&date=2026-10-31
```

页面从响应中读取：

```json
{
  "durationMinutes": 3
}
```

前端直接将该值显示为“昨日分钟”。

### 接口二：近 7 日趋势

```http
GET /learning-stats/daily?deviceId=dev-local-001&days=7
```

其中 `2026-10-31` 对应的数据点表现为：

```json
{
  "date": "2026-10-31",
  "durationMinutes": 0
}
```

前端直接将该值用于柱状图，因此柱子高度和柱顶数字均为 0。

> 当前未保留本次请求的完整原始 JSON。以上字段值是根据页面数据绑定链路确认的关键结果；排查时请重新抓取两份完整响应存档。

## 三、预期行为

对于同一设备、同一自然日，两个接口的时长统计必须一致：

```text
parent-report.durationMinutes
=
daily 数组中 reportDate 对应日期的 durationMinutes
```

如果原始会话记录证明 10 月 31 日确实使用了 3 分钟，则预期结果为：

- 家长报告：`durationMinutes = 3`
- 每日趋势中 `2026-10-31`：`durationMinutes = 3`

## 五、优先排查方向

### 1. 两个接口是否读取了不同的数据源

重点检查：

- `parent-report` 是否直接统计会话表；
- `daily` 是否读取每日统计表、物化视图或缓存；
- 每日统计任务是否遗漏了 `2026-10-31` 的数据；
- 会话已经写入，但每日聚合尚未执行或执行失败；
- 聚合任务是否只统计到昨天之前，或错误排除了最近一天。

**这是当前最优先的方向。**家长报告同时存在时长和互动次数，而趋势为零，很像“实时明细有数据，但统计快照未更新”。

### 2. 日期和时区边界是否一致

分别打印两个接口实际使用的查询起止时间，例如：

```text
parent-report:
start = ?
end   = ?

daily:
start = ?
end   = ?
```

检查：

- 是否一个使用 UTC，另一个使用东八区；
- 是否按 `createdAt` 的 UTC 日期直接分组；
- 是否先转换为业务时区，再生成 `YYYY-MM-DD`；
- 是否使用左闭右开区间：

```text
[2026-10-31 00:00:00, 2026-11-01 00:00:00)
```

- 会话跨天时，两个接口按开始时间还是结束时间归档是否一致。

### 3. 会话过滤条件是否一致

对比两个接口的 SQL 或 ORM 查询条件：

- 会话状态：是否只统计 `completed`；
- 是否排除了异常中断、未结束或测试会话；
- 是否过滤了 `free_chat`；
- 是否要求必须存在 AI 回复；
- 是否只统计有效时长大于某个阈值的会话；
- 是否一个按设备当前配置统计，另一个统计设备全部历史配置。

本例 5 次互动均来自自由对话，需特别确认 `daily` 是否遗漏了 `free_chat` 模式。

### 4. 设备归属是否一致

确认两个接口查询的是同一个实体：

```text
deviceId = dev-local-001
```

检查是否存在：

- 设备 ID 与孩子 ID 混用；
- 设备解绑、重新绑定后历史数据归属变化；
- 一个接口查询设备表主键，另一个查询设备序列号；
- 聚合数据仍挂在旧设备或旧孩子档案下。

### 5. 缓存或异步更新延迟

检查：

- `daily` 是否命中了旧缓存；
- 缓存 Key 是否包含 `deviceId`、日期范围和统计口径；
- 新会话结束后是否使每日统计缓存失效；
- `parent-report` 是否绕过了缓存，因此取得了较新的数据；
- 页面下拉刷新后，`daily` 是否仍然返回旧值。

### 6. 时长字段及单位

虽然 `3` 与 `0` 的差异不太像普通四舍五入问题，仍建议确认：

- 数据库存储的是秒还是毫秒；
- 两个接口转换成分钟的方式是否一致；
- 是否存在空值被转换成 0；
- 是否一个接口使用原始时长，另一个使用有效学习时长。

## 六、建议排查步骤

### 第一步：固定并保存两份原始响应

在同一账号、同一设备、同一时刻分别请求：

```http
GET /learning-stats/daily?deviceId=dev-local-001&days=7
GET /learning-stats/parent-report?deviceId=dev-local-001&date=2026-10-31
```

保留完整响应，并记录：

- 请求时间；
- 后端版本或提交号；
- 当前环境；
- 数据是否来自缓存；
- 实际查询参数。

### 第二步：回查原始会话明细

按产品约定的业务时区查询该设备在 10 月 31 日的会话，至少包含：

```text
sessionId
deviceId
mode
status
startedAt
endedAt
createdAt
durationSeconds / durationMs
```

先以原始明细确认正确答案究竟是 3 分钟、0 分钟，还是其他数值。

### 第三步：对比两个接口的聚合链路

分别记录：

- 查询的表或视图；
- 完整过滤条件；
- 时区转换；
- 日期分组字段；
- 时长计算公式；
- 缓存读取与失效逻辑；
- 异步任务执行时间和执行结果。

### 第四步：做一次新增会话验证

1. 在该设备产生一段已知时长的新会话；
2. 等会话正常结束；
3. 同时刷新两个接口；
4. 检查二者是否同步增加；
5. 若只有 `parent-report` 增加，重点检查 `daily` 的聚合任务和缓存；
6. 若只有 `daily` 增加，检查 `parent-report` 的过滤条件和报告快照。

## 七、推荐修复方式

### 根本修复

让两个接口复用同一个每日时长聚合逻辑，例如：

```text
getDailyDuration(deviceId, reportDate)
```

由它统一负责：

- 数据源选择；
- 会话过滤；
- 业务时区；
- 日期边界；
- 时长单位及舍入；
- 缓存策略。

`parent-report` 和 `daily` 只负责组织各自响应，不再分别实现一套时长统计。

### 不建议的处理

不建议前端简单地把柱子中的 `0` 替换成家长报告的 `3`。这只能掩盖显示矛盾，无法解决接口数据不一致，也会影响其他设备和其他日期。

---

## 八、修复验收标准

1. 同一设备、同一日期，两个接口的 `durationMinutes` 必须相等。
2. 若原始明细确认本例为 3 分钟，则两处都应返回 3。
3. 新增一段已知时长的会话后，两处按约定的数据更新时效同步变化。
4. 跨 UTC 日期但未跨业务自然日的会话，应归入同一个业务日期。
5. 多设备之间不能串数据。
6. 零使用日期仍应返回 0，不能因为修复而生成虚假时长。
7. 增加接口契约测试：

```text
parent-report.durationMinutes
===
daily[reportDate].durationMinutes
```
